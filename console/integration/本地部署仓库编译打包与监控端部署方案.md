# 本地部署仓库编译打包与监控端部署方案

2026-11-03，V1.1 设计方案，已纳入策略管理总方案 V5。实施状态：deploy 仓库已有构建/部署脚本，监控端已接入 list/status/apply/rollback，并单独记录遥测恢复结果；本地模拟测试通过，Radxa 实际更新、回退及动作验收尚未执行。本次监控端修订未修改机器人部署脚本或安装系统服务。这里的“固件”指 ARM64 应用程序部署包，不涉及系统镜像或舵机固件刷写。

## 1 使用方式

编译和部署能力归本地 `openchicken_deploy` 仓库所有。监控台配置一次仓库绝对路径，读取该仓库导出的版本列表，用户选择机器人及版本后调用仓库部署脚本。脚本可以独立在终端使用，监控台不复制一套部署逻辑。

```text
本地 deploy 仓库
  build/radxa/run.py → 编译、测试、打包 → dist/radxa/<build_id>/
                                           ↓ 版本列表
监控台配置页 → 选择机器人 / 部署版本 → deploy/radxa/deploy.py
                                           ↓ SSH / SCP
Radxa releases/<build_id>/ → 切换 current → 启动所选服务
                                           ↓
监控台显示结果，并保存到该机器人档案
```

“本地仓库路径”指运行监控台后端的电脑上的路径。浏览器位于另一台电脑时，也填写后端电脑路径，不是浏览器电脑路径。

第一版监控台提供“刷新版本、部署所选版本、查询机器人当前版本、恢复上一版”；编译先在终端执行。后续增加“编译新版本”按钮时调用同一个构建脚本即可，无须重写构建逻辑。

## 2 仓库目录与版本命名

固定导出目录采用已有 gitignore 覆盖的 `dist/`：

```text
openchicken_deploy/
  build/radxa/
    run.py                         # 改造已有编译入口
    build.sh                       # 复用已有容器内构建
    package.py                     # 改造已有打包入口
  deploy/radxa/
    deploy.py                      # 新增：查询、部署、恢复
    *.service                      # 服务模板
  dist/radxa/
    <build_id>/
      openchicken-<build_id>.tar.gz
      openchicken-<build_id>.tar.gz.sha256
      build-info.json              # 包内元数据的同一份副本，供版本列表快速读取
  .cache/radxa/
    cargo/                         # 共用依赖缓存
    target/                        # 共用编译缓存
    jobs/<build_id>/               # 源码快照、日志和中间文件
```

`build_id` 示例：`v0.17.8-api48-20261103T083500Z-3828ce9`。组成是 Cargo 软件版本、IPC API、UTC 构建时间和 Git 短提交号；监控台显示时转换成本地时间。目录创建采用不覆盖方式，同秒重名加序号。

允许构建本机未提交修改；此时附 `-dirty-<源码摘要>`，记录基础提交号和实际源码摘要，不能把产物标为纯净提交构建。已完成的版本目录不覆盖，重新编译产生新版本。

`dist/`、`.cache/`、本机部署结果和开发记录不提交 Git；脚本、公开模板和 README 提交 Git。不增加可与目录内容失去同步的全局版本数据库，版本列表直接扫描已完成目录。

## 3 编译脚本职责

沿用 `build/radxa/run.py`，由脚本定位仓库根目录、读取版本和 API，自动生成 build_id。默认不再要求填写 `--output`。

拟定调用形式：

```sh
python /home/cyz/openchicken/openchicken_deploy/build/radxa/run.py --image-ready
```

流程：

1. 读取版本、提交、工作区修改状态和本次 UTC 时间，建立独立构建任务目录。
2. 从 Git 管理的源码及未忽略的新源码制作快照；包括本次需要的本机修改，排除 `.git`、`dist`、`.cache`、开发记录、凭据和已生成文件。符号链接不允许把仓库外文件意外带入快照。
3. 使用现有 Docker 构建环境及固定缓存，运行与本次程序相关的原生测试，再交叉编译 ARM64 程序。初次镜像/依赖准备与重复编译分开显示，不宣称未准备依赖的新机可以直接离线构建。
4. 在打包阶段收集二进制、桥接代码、服务模板和依赖说明，检查目标架构，生成校验清单。
5. 完整生成归档、外部哈希及同一份 build-info 后，将临时输出目录原子发布到 `dist/radxa/<build_id>/`。
6. 返回版本、包路径、大小和构建结果。失败保留任务日志，不在可部署版本列表中出现一个未完成包。

输出目录位于源码仓库内后，必须替换当前不区分 Git 忽略规则的整目录复制方式，否则会递归复制自身或历史部署包。缓存路径也不能再依赖上一轮临时构建目录。

构建需要本机 Docker 权限和已有工具环境；脚本不自行修改主机系统权限、不安装常驻构建服务。

## 4 统一部署包内容与桥接代码来源

```text
openchicken-<build_id>/
  bin/                             # 原生 ARM64 程序
  console/agent/                   # runtime bridge 所需 Python 源码
  console/protocol/                # bridge 所需协议代码
  models/                         # 源码内的辅助识别模型，如需要
  reference/radxa/                 # 当前 Radxa 服务及启动入口模板
  reference/robotd.toml            # 默认参考，不直接覆盖机器配置
  runtime-dependencies.json
  build-info.json
  SHA256SUMS
  README.md
  LICENSE
```

当前通用 package.py 主要收集原生二进制、辅助模型和上游 service；本次 API48 包则是另外整理出的二进制、桥接代码及 Radxa 模板。实施时合并为上面一个正式格式，不保留两套相互不一致的打包流程。

机器人端桥接代码目前属于同级 console 项目。第一版不复制一份源码长期维护：构建入口支持 `--console-source <路径>`，默认尝试当前独立监控仓库布局 `<deploy仓库父目录>/console/openchicken_console`；目录必须通过 bridge 文件清单校验，未找到时由终端显式指定。`--console-source` 统一指包含 `console/agent`、`console/protocol` 的工程根目录；从监控台调用构建时，由后端自动传入当前监控工程根目录。因此用户在页面只需填写 deploy 仓库路径。

打包只收集 bridge 的明确文件清单，不复制整个 console 目录或私有配置，并记录这些文件的摘要。缺少 bridge 源码时在构建前明确报缺失，不能输出一个名为完整包的残缺产物。独立克隆 deploy 仓库的开发者可通过上述参数指定 console 源码。

ONNX 动作策略、ONNX Runtime/pyzmq 等运行依赖和每台机器配置继续独立存放。程序包声明需要的依赖，复用已安装环境；依赖安装属于新机初始化。监控前端也不装到机器人，前端升级与本体程序版本分开记录。

包不携带可自动执行的 preinstall/postinstall 钩子；部署行为由用户选择的本地仓库脚本确定。

## 5 部署包元数据

扩展已有 `build-info.json`，不再增加一份同义 manifest：

| 字段 | 内容 |
| --- | --- |
| `package_format` | 部署包结构版本，第一版为 1，与 IPC API 分开 |
| `build_id`、`version`、`api_version` | 发布标识、Cargo 软件版本、IPC API |
| `revision`、`dirty`、`source_sha256` | 基础提交与实际构建源码身份 |
| `build_time`、`target` | UTC 时间与 aarch64 目标 |
| `console_bridge_sha256` | 本包桥接源码摘要 |
| `binaries` | 本包程序清单 |
| `service_profiles` | runtime 基础服务、可选 native_pad 服务及启动顺序 |
| `required_runtime` | ONNX Runtime、Python 等实际依赖要求 |

包内和目录旁的 build-info 内容一致。包本身的 SHA256 放在旁置 `.sha256` 文件中，避免把归档哈希写进归档自身。文件哈希用于传输完整性，不把本地无签名包说成上游签名发布。

## 6 部署脚本接口

新增 `deploy/radxa/deploy.py`，作为唯一部署入口。以下命令为拟定接口，当前尚不存在：

```sh
# 只列本地已完成部署包，不连接机器人
python <repo>/deploy/radxa/deploy.py list --json

# 读取机器人当前发布、服务状态
python <repo>/deploy/radxa/deploy.py status --target-file <target.json> --json

# 将选定发布部署到目标机器人
python <repo>/deploy/radxa/deploy.py apply \
  --build-id <build_id> --target-file <target.json> --json

# 恢复这台机器记录的上一版
python <repo>/deploy/radxa/deploy.py rollback --target-file <target.json> --json
```

仓库路径从脚本自身推导；`build_id` 必须对应本仓库 dist 中的版本，不是任意 shell 文本。target 文件由监控后端根据所选机器人档案生成，包含 profile_id、地址/端口、SSH 用户、运行用户、部署根目录、socket 和服务组合，不包含密码或私钥。

复用现有 SSH 主机信任和认证处理。密码仅通过已有会话认证辅助通道提供，不放进命令行、target 文件、日志或档案；SSH agent 也可沿用。部署脚本使用参数数组调用本机进程，并正确引用远端 shell 参数。

`--json` 输出逐行事件，普通终端模式输出可读进度。例如：

```json
{"event":"progress","step":"upload","message":"正在上传所选版本"}
{"event":"progress","step":"activate","message":"正在切换当前发布"}
{"event":"result","status":"success","build_id":"示例版本","previous_build_id":"上一版本"}
```

普通失败返回非零退出码及原因；SSH 中断而远端结果未知时单独报告 `unknown`。不把进度百分比、上传成功或子进程退出码单独当成部署完成。

## 7 Radxa 上的发布与配置

沿用已固化布局：

```text
<deploy_root>/
  releases/<build_id>/             # 发布程序与 bridge
  current -> releases/<build_id>
  config/                         # robotd.toml、agent 身份等机器配置
  policies/                       # 独立策略文件
  deps/                           # 已安装运行库
  state/deployments/               # 简短部署结果，便于 SSH 中断后读取
```

apply 的具体顺序：

1. **读取现状**：读取 current、启用服务及实际运行状态；确认目标架构、已有依赖、目标目录和服务管理权限，展示将变更的版本及服务。检查只覆盖这次更新直接需要的条件。
2. **上传与展开**：通过 SCP 上传，核对归档哈希，展开到临时发布目录，核对包内清单；归档条目不得越过目标目录。文件完整后再形成正式 releases 目录，上传阶段不停止运行中的程序。
3. **停止与切换**：操作员按现有流程停止、松力；脚本核实已停止运动且松力后停止本次服务组（不能仅以策略未使能推断已断矩；状态不明则报告条件未满足），记下旧发布和服务状态，再原子替换 current。
4. **启动与读取**：按依赖顺序启动服务，读取实际发布身份、robotctl 查询和服务结果。监控台另显示遥测是否重新连通，不把本地缓存当成新版本反馈。
5. **落记录**：写一份结果到板端 state，主机保存完整部署任务并更新机器人档案。部署结束不自动使能策略或试动作。

默认服务组只更新当前 runtime 所需的 robotd、tofd、openchicken-agent；原生蓝牙组包括 configd、padd。目录中有 13 个程序不表示启动 13 个服务。

对于已启用的蓝牙组，升级保留其启用状态并一起更新。首次安装/启用蓝牙服务是明确选项，使用模板渲染当前用户和根路径，先显示修改项，不因上传了 padd 程序而自动启用。

config、标定参数（含 Homing Offset）、policies、deps 不被参考文件覆盖。需要变更配置格式时只展示本次必要差异；本次 `lb_*` 按键迁移写在版本说明中，不能无提示重写整份机器人配置。

### 系统权限

当前固化流程通过管理员 SSH 管理 systemd，不使用 sudo。部署脚本沿用这一方式；运行用户仍是 openchicken1。读取、上传可以使用普通用户，服务安装/启停及必要文件归属设置必须使用已授权的管理员连接。

监控台可在该机器的部署设置保存管理员用户名，认证仍是当前会话，不持久化密码。不把 root 权限加入 agent，不新增常驻特权管理程序，也不把普通用户的只读 SSH 成功误认为具备部署权限。

普通程序升级与首次服务安装分开呈现。新机缺少系统依赖、设备权限或基础服务时，报告缺失并转到初始化流程；第一版不顺带执行系统镜像、设备树、音频驱动或固件安装。

## 8 恢复与中断

旧 releases 目录保留。rollback 读取该机器上一次成功切换记录，按同样的停止、切换、启动和查询流程恢复上一版；用户也可明确选择保留的历史发布。

启动失败时显示失败服务和当前 current 指向，提供“恢复上一版”；第一版不增加自动来回切换的恢复状态机。SSH 超时或主机重启后先执行 status，读取板端结果和真实服务状态，不自动补发 apply。

若本次还安装了服务模板，恢复需使用对应服务文件备份和原启用状态；纯程序切换不能被描述成已经撤销系统服务配置。第一版主要验收已有机器的软件升级，首次蓝牙服务启用单独验收。

每台机器人同一时刻只运行一个部署任务，复用现有任务忙碌状态；不引入队列服务、分布式锁或第二套控制所有权。

## 9 监控台页面与档案

在“配置测试 → 程序部署”中配置本机仓库路径。路径确认后才调用该仓库固定入口；切换机器人不会运行脚本，填写路径不会拉 Git、执行下载代码或部署。

页面上方显示所选机器人、当前运行版本和仓库路径；版本表包含时间、软件/API 版本、提交、dirty 标记、包大小。按构建时间倒序，默认只选中最新版本，不自动部署。

点击部署后展示目标机器、所选版本、服务范围和需要的会话认证，确认后开始；日志显示上传、切换、启动和读取结果。普通升级不增加多轮重复确认。初始化/首次启用服务作为明确操作项展示其系统变更。

机器人档案按稳定 profile_id 保存：

- 当前已确认运行的 build_id、提交、API、读取时间。
- 包路径及哈希、升级前后发布、服务组合、开始/结束时间、结果和日志引用。
- 每次部署、恢复、失败或结果未知的历史记录。
- 物理测试结果单独关联版本；程序启动成功不自动写成动作验收通过。

本机仓库路径属于控制台主机设置；机器地址、运行用户、远端根目录及部署历史属于机器人档案。多台机器可以共用一个本地仓库，历史不能串到另一台机器。

## 10 最小实施顺序

| 步骤 | 修改 | 验收 |
| --- | --- | --- |
| 1 编译输出固化 | 改 run.py/build.sh/package.py，固定 dist 和缓存，自动时间版本命名，统一包内容 | 连续构建生成独立版本；不会递归复制输出；失败包不出现在列表；桥接与原生文件可追溯 |
| 2 部署脚本 | 新增 list/status/apply/rollback，沿用 SSH/SCP 和已固化发布布局 | 假 SSH 验证命令和结果；上传失败不切换；系统服务状态及上一版可恢复 |
| 3 监控端适配 | 仓库路径、版本表、脚本进度、结果和档案记录 | 页面及命令行走同一脚本；包和机器人不会选错；没有重复部署实现 |
| 4 Radxa 实机验收 | 对已配置机器执行一次程序更新、查询和恢复 | 实际版本与服务一致，遥测恢复，配置和策略保留；不自动触发运动 |
| 后续 | 可选页面编译按钮、新机初始化向导 | 调用已有脚本；只为新增加的功能补测试 |

第一版不做云端固件仓库、自动升级、系统刷机、脚本插件市场或全硬件重新验收。需要依赖/服务安装的初始化工作不伪装成普通版本切换。
